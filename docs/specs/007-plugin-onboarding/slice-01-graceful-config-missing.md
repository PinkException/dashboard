## Slice 007-01 — graceful config-missing message

**Goal:** when the dashboard config is absent, the snapshot routine tells the user
what to do instead of throwing a raw `ENOENT` stack trace — so a fresh plugin
installer who runs the routine before ever opening the dashboard gets a next step,
not a crash.

**DoR:**
- ✅ A1 probed (spec): a missing config throws a bare `ENOENT` from `loadConfig`
  (`src/scan.mjs:127`).

**Acceptance Criteria:**

1. **`loadConfig` raises a clear, typed missing-config error.** When the resolved
   config path does not exist, `loadConfig` throws an error that is
   programmatically distinguishable from other failures (e.g. a `code` /
   `kind: 'config-missing'` property, or a dedicated error class) and whose message
   names the missing path and points at `/dashboard:open`. It must **not** leak a
   `node:fs` stack frame as the primary signal.
2. **The `snapshot.mjs` CLI exits cleanly on a missing config.** `snapshot.mjs
   --all --auto [--if-changed]` with no config present prints a single friendly
   line to stderr — the missing path plus "run `/dashboard:open` to create one" —
   and exits **non-zero with no stack trace**. (Today it crashes with an uncaught
   `ENOENT`.)
3. **Malformed JSON stays a distinct, honest error.** A config that exists but is
   not valid JSON is reported as a *different* error (parse/other), not
   misclassified as "missing" — the user must not be told to create a file that is
   already there.
4. **No behaviour change when the config is present.** With a valid config,
   `loadConfig` and the routine behave exactly as before (same projects, same
   output). Other callers of `loadConfig` (the server, `/dashboard:open` flow) are
   not broken by the new error type.
5. **Tested, non-vacuously, against a temp path.** Tests (via `DASHBOARD_CONFIG` /
   an explicit path to a temp dir, never the real config) cover: missing config →
   typed error from `loadConfig` + clean non-zero CLI exit with the pointer
   message and no stack trace; malformed JSON → distinct error; present config →
   unchanged. Each new test is shown to fail if its guard is removed. `npm test`
   passes, including `test/no-leaks.test.mjs`.

**Notes / scope.**
- Scope is the *missing-config* UX only. It does not change what the routine
  writes, the config schema, or `/dashboard:open` (which already handles the
  missing case its own way — this slice brings the CLI/routine path up to the same
  standard).

### Deviation log (after reconciliation)

Implementation matched the ACs; no scope drift. Notes:

- **Error contract chosen.** `loadConfig` throws a `ConfigMissingError`
  (`name: 'ConfigMissingError'`, `code: 'CONFIG_MISSING'`, `configPath`) — callers
  discriminate on `code` without string-matching the message. The `try` wraps only
  `fs.readFileSync`; `JSON.parse` sits *outside* it, so a malformed present file
  surfaces as a distinct `SyntaxError` (AC3) and the ENOENT catch cannot swallow an
  unrelated failure.
- **Deliberate scope boundaries (both reviewers noted; both in-scope-correct):**
  - `EACCES` (or any non-ENOENT I/O error) on the config read is re-thrown raw. Only
    the *missing*-config UX is in scope.
  - A *malformed* (present) config at the `--all` CLI still prints a raw
    `SyntaxError` stack. AC3 required only distinct *classification* (delivered); a
    friendly malformed-case message is a follow-up (captured in `docs/inbox.md`).
- **Server caller unaffected.** `src/server.mjs` already catches `loadConfig` errors
  generically via `err.message`, so it benefits from the friendlier text with no
  change. Its *own* hand-rolled missing-config message points at
  `dashboard.config.example.json` rather than `/dashboard:open` — a user-facing
  divergence, captured as a follow-up in `docs/inbox.md` (out of this slice's scope).
- 124/124 tests green including `test/no-leaks.test.mjs`; each new test shown to fail
  before its guard existed (non-vacuous), including the CLI "no stack trace" assertion.
